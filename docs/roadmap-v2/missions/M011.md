## 1. Objectif fonctionnel et condition de sortie

Faire de STUDIO IA un outil confortable pour traiter de nombreuses vidéos sans perte de contrôle, avec inspection visuelle fiable avant les traitements lourds.

### Démonstrations ou résultats indispensables

- A/B temporel synchronisé, zoom et comparaison zones sensibles.
- File batch, profils versionnés, étiquettes d’avancement.
- Projets locaux exportables, historique et reprise sans suppression de médias.

### Ce qui reste hors périmètre

- Pas de timeline de montage créatif dans cette version.
- Pas d’aperçu amélioré simulé.
- Pas de lancement automatique de batch coûteux sans préflight et consentement.

## 2. Architecture et discipline de compatibilité

Le point de départ n’est pas un dépôt vierge : la version CPU `0.3.0a2` a déjà une GUI PySide6, un pipeline FFmpeg/ffprobe, une CLI, SQLite, des protections de fichiers, des tests Windows/Linux et une PR de consolidation. Toute refonte globale non indispensable est interdite. Inspecter le code réellement présent et adapter les nouvelles interfaces sans casser ce socle. Le cahier M004 initial existe déjà dans `docs/mission-004/` ; ce programme le complète et ne l’efface pas.

### Contrats obligatoires de chaque nouvelle fonctionnalité

1. **Entrée** : média contrôlé, timebase rationnelle, provenance et hash, paramètres validés, chemins canoniques.
2. **Capacité** : moteur, modèle exact, version, dépendances/permissions/licence, matériel compatible et niveau de qualification.
3. **Exécution** : traitement contrôlé et annulable, budget disque/mémoire, progression réelle ou indéterminée.
4. **Sortie** : export dans un nouveau fichier, preuve de décodage, dimensions/durée/PTS/audio/couleur selon politique.
5. **Diagnostic** : logs locaux expurgés, code erreur utilisateur lisible, tests reproduisibles, non-régression.
6. **État** : `PASS`, `FAIL`, `SKIP`, `BLOCKED` tracés au commit, OS, matériel, versions et artefacts.

### Assertions transversales

- `source_sha256_before == source_sha256_after`; pas d’écrasement des sources, sauvegardes ni sorties existantes.
- Si un résultat est déclaré `PASS` : fichier de sortie réellement créé, lisible, décodable intégralement et provenance/versions archivées.
- Si un traitement est annulé, crash, OOM ou incompatible : aucun fichier final annoncé réussi; explication, logs et nettoyage contrôlé.
- Comparaison sur mêmes timestamps et avec même transformation colorimétrique, ou `NOT_APPLICABLE` explicite.
- Tests positifs et négatifs sur Windows/Linux lorsque pertinents; GPU réel indispensable pour déclarer un moteur NN opérationnel.
- Mise en place d’un test CI sur source synthétique; média réel licencié testé localement et jamais téléversé sans droit.

## 5. Critères d’acceptation bloquants

- [ ] **AC-011-01** : L’interface déclenche uniquement des traitements réellement implémentés.
- [ ] **AC-011-02** : Batch garde le contrôle et ne remplace aucune sortie existante.
- [ ] **AC-011-03** : Comparaison temporelle alignée ou explicitement refusée.

### Matrice de décision

| État | Définition | Autorise le lot suivant ? |
|---|---|---|
| PASS | Test réel au SHA exact, preuve lisible | Oui, si toutes les gates bloquantes PASS |
| IMPLEMENTED_UNVERIFIED | Code présent, test réel absent | Non pour les gates de production |
| SKIP | Non exécuté avec motif précis | Seulement si le lot facultatif est isolé |
| BLOCKED | Prérequis logiciel/hardware/droit absent | Non ; réparer la précondition |
| FAIL/REGRESSION | Assertion invalide ou ancien test cassé | Non |

## 6. Risques techniques, rejets et fallbacks

- Moteur de lecture vidéo Qt peut manquer selon OS; fallback extractions synchronisées honnêtes.
- La queue peut saturer le disque, préflight obligatoire.
- Migration SQLite doit être testée avec anciennes données.

**Fallback défini :** préserver les fonctions déjà qualifiées, isoler le composant non compatible, proposer mode CPU si disponible, conserver les preuves d’échec et ne pas engager de coût. Ne pas convertir un blocage GPU en une annonce de « GPU intégré ». Le propriétaire doit autoriser explicitement toute dépense, installation personnelle, diffusion de média sensible, fusion ou saut vers création.

## 7. Contrôle qualité et sécurité

Rejouer `pytest -q -ra`, les scénarios FFmpeg/GUI pertinents et les tests de non-régression historiques de M003. La CI actuelle n’a pas besoin de GPU pour rester valide; ajouter un job GPU uniquement s’il existe une infrastructure approuvée. Les métriques doivent être publiées avec leur protocole, leur corpus et leurs limites. L’avis humain ne peut venir que d’une revue humaine authentique. Toute fonctionnalité de sécurité (restriction réseau, no-clobber, licence et hash modèle) doit être testée négativement, pas uniquement documentée.

## Règles transversales de développement

**Architecture** : préserver `src/studio_ia` et les contrats existants sauf migration explicitement testée. Les sous-processus utilisent argv validés sans `shell=True`, limite de durée et gestion correcte des groupes; toute ressource temporaire possède une identité de job et une politique d’effacement sûre. Conserver des schémas versionnés, des tests de migration et une CLI fonctionnelle indépendamment de Qt. Une décision différente est admise si une ADR expose sa motivation, ses compromis et les tests de non-régression.

**Réalité du résultat** : une vidéo plus grande en pixels n’est pas nécessairement meilleure. Une métrique PSNR/SSIM/VMAF n’est exploitable qu’avec références alignées et conditions applicables; jamais un score « photoréalisme 100 % ». Toujours documenter les détails potentiellement hallucinés, le flou résiduel et les cas de détérioration. Pour les véritables médias humains, ne pas prétendre à une identité exacte reconstruite si la source n’offre pas les détails.

**Gestion des livrables** : les Markdown de missions sont publiés en Git sur une branche de documentation. Les PDF sont des éditions de lecture équivalentes. Ne pas incorporer de poids ML volumineux, médias privés ou binaires au Git sans stratégie approuvée. Les preuves peuvent être des fichiers courts, manifestes et artefacts CI; les liens expirants doivent avoir sauvegarde indépendante.

**Porte inter-missions** : une mission *décrite* n’est pas une mission *réalisée*. Codex n’enchaîne pas automatiquement vers une mission incompatible avec les ressources ou les autorisations. Les domaines déjà en PASS restent protégés par CI et peuvent toujours faire l’objet de correctifs ciblés avant le lot suivant.
